# IdentityHub — Design Decisions & Assumptions

Why this is built the way it is: the reasoning, the boundaries we drew, and the
assumptions we made where the brief was open-ended.

**If you have ten minutes, the table below is the whole document.** Each row is a
decision and its one-line reason; the section it points at is there if you want
to argue with one.

| # | Decision | Because |
|---|---|---|
| **0** | The Jira credential is treated as an NHI, not as config | It is exactly what this product exists to find: long-lived, machine-used, broad write access. Encrypted per tenant, revocable, attributable, never logged |
| **1** | Postgres, Redis, Temporal, a KMS, Compose — and nothing else running | Each earns its place with a job no other one does. Redis holds signed-out tokens because a key with a TTL is that job's exact shape |
| **1** | Queries are SQL, generated by sqlc. No ORM | The invariant that matters — *no query crosses an account boundary* — has to be readable, and it is, as SQL with its `where` visible |
| **1** | Every write is a transaction; the app role cannot change the schema | A rule a reader verifies by looking beats one re-derived per call site. `audit_events` additionally has UPDATE and DELETE revoked |
| **2a** | We sign people in with a password, and that is the part production deletes | Every customer has an identity provider. Building it proves the seam is real: the token we mint is the shape theirs is, so swapping is one file |
| **2a** | Tokens are signed HMAC-SHA256, algorithm **pinned, not read** | A verifier that trusts the header is one a caller can talk out of checking — `alg: none` and RS256→HS256. Five forgeries covered by test |
| **2a** | Sign-out revokes the token server-side, in Redis, until its own expiry | A logout that only clears the browser is not one: a copy taken beforehand keeps working. This is not a session store — nothing is written at sign-in |
| **2a** | bcrypt for passwords, plain SHA-256 for API keys | Opposite problems. Low-entropy human input needs an expensive guess; 256 bits of CSPRNG output has no dictionary, so a work factor buys nothing |
| **2a** | We did **not** bind tokens to IP or User-Agent | Rejected on merits: both break real users and neither stops a thief. The mechanisms that work — refresh rotation, DPoP — belong to the provider |
| **2b** | API keys are the second credential, for machines only | A CI job cannot complete an interactive flow. Hashed, shown once, tenant discovered from the key itself |
| **3** | One door to every connector: `Execute`, carrying JSON | An earlier version had two paths and a type switch. A seam that is *sometimes* the seam is not a seam |
| **3** | Three packages: `connector`, `capabilities/issuetracker`, `connections` | The import graph is the proof — the port depends on nothing of ours, a capability depends on the port, and only `connections` touches the database or the key service |
| **4** | Tenancy comes from the token and nothing else | No request type has a field for an organization. Acting in another tenancy means forging a signature, not editing a request. Tested against a sibling account |
| **4** | Application-level scoping, **not** Postgres RLS | RLS is stronger and needs a page of explanation before it can be reviewed. This boundary fits on one screen |
| **5** | The tenancy is inside the ciphertext, not beside it | Decryption fails if the scope does not match, so a swapped row is unusable rather than merely unauthorized |
| **7** | The OpenAPI document decides routing, authorization **and** shapes | Routing generated, authorization read at boot, responses validated in the suite. Reading it requires signing in |
| **7** | A replayed `Idempotency-Key` is a success with `created: false` | The caller asked for the finding to exist and it does. Not a conflict |
| **8** | Only two operations are durable; the reads are not | Temporal is easy to over-apply. Wrapping a `SELECT` in a workflow would undercut the two places it genuinely earns its keep |
| **8** | Credentials never enter workflow history | History is persisted and replayable. The credential is fetched inside the activity and dies with it |
| **9** | What we deliberately did not build, and why | Brute-force lockout, refresh tokens, a second connector, RLS, k8s, webhooks — each with the reason, not silence |

Known gaps are stated where they belong rather than collected at the end, and
each is marked **deliberately** or **not fixed** so the two are never confused.

## 0. Framing: the integration credential *is* an NHI

IdentityHub is a Non-Human Identity platform. The moment a tenant connects their Jira
workspace, this application creates exactly the kind of artifact the product exists to
find: a long-lived, machine-used credential with broad write access to a SaaS system.

We treat it accordingly, and that framing drives most decisions below:

- it is **encrypted at rest by a key service**, with the tenancy bound into the
  ciphertext so a row cannot be moved between accounts (§5),
- it is **rotatable** and **revocable** without a redeploy,
- every use of it is **attributable** to a human or an API key in the audit log,
- it is **never logged**, never returned by any API, and redacted in error paths,
- we prefer **short-lived tokens** where the provider supports them (see §3).

## 1. Stack

Things that run: separate processes, images and programs. A Go library is not a
stack choice — the table after it says which ones matter and which file owns
each.

| | Choice | Why |
|---|---|---|
| Language | **Go 1.26** | Strong stdlib crypto and HTTP story; one static binary per process |
| Database | **PostgreSQL 16** | Relational tenancy model; two-layer org/account isolation |
| Cache / ephemeral store | **Redis 7** | Signed-out tokens, and nothing else. A key with a TTL is exactly the shape of "stop honouring this until it would have expired anyway". Opened by `internal/cache`, used by `internal/auth` — §2a |
| Durable execution | **Temporal** | The two operations that are multi-step, cross a network we do not control, and are worse than useless half-done — §8 |
| Key service | **floci** locally, AWS KMS in production | Real KMS wire protocol with no account and no auth token, so the code path in development is the one that runs in production. Only `SECRETS_KEEPER_URL` differs |
| Reverse proxy | **nginx** | Serves the built interface and proxies `/api`, so the browser sees one origin and there is no CORS to configure |
| Packaging | **Docker Compose** | `docker compose up` is the entire setup story |

Build-time programs, which produce code rather than run beside it:

| | Choice | Why |
|---|---|---|
| SQL → Go | **sqlc** | Queries stay SQL, checked against the real schema at build time. No ORM: the query that must not cross a tenant boundary should be readable as SQL — §1 below |
| Migrations | **goose** | Plain SQL, applied by a compose step before the API starts |
| Spec → Go | **oapi-codegen** | Routing and parameter types generated from `api/openapi.yaml`, so an operation with no handler does not compile — §7 |
| Interface | **Vite** building **React** | Produces static files nginx serves. TanStack Query for server state, react-hook-form + zod for forms |

### The libraries that carry a decision, and where each one lives

Most dependencies are unremarkable. These five are load-bearing, and each is
answerable from one file:

| Library | Owns | File |
|---|---|---|
| `golang.org/x/crypto/bcrypt` | Hashing and checking a password. Chosen over SHA-256 for a reason that is the opposite of the API key's — §2a | `internal/auth/password.go` |
| `golang-jwt/jwt/v5` | Issuing and verifying access tokens. The security decisions are ours and live in `parserOptions`; the base64, HMAC and expiry arithmetic are the library's — §2a | `internal/auth/token.go` |
| `redis/go-redis/v9` | Talking to Redis. Opened once by `internal/cache` and handed to whatever needs it; `internal/auth` declares the three-method interface it actually uses, so the dependency points at the consumer — §2a | `internal/cache/cache.go` |
| `gocloud.dev/secrets` | Encrypting a stored credential. The provider is a URL, so AWS KMS, GCP, Azure or Vault is a configuration change — §5 | `internal/crypto/` |
| `ctreminiom/go-atlassian` | Talking to Jira. Atlassian ships no official Go SDK; this is the maintained one, and it independently makes the two non-obvious endpoint choices this project had to research — §3 | `internal/connector/jira/` |

`echo` routes, `pgx` connects and `kin-openapi` reads the document. They are
tools doing their obvious job and carry no argument.

### Configuration is read once, validated, and fatal if wrong

Each binary declares its own configuration struct, parsed from the environment
with [`sethvargo/go-envconfig`](https://github.com/sethvargo/go-envconfig) and
validated before anything else happens. There is no `os.Getenv` in the codebase
outside of that.

A binary asks only for what it uses. The worker has no listen address and no
token issuer, because it serves no HTTP; the migrate
step does not read the key service, because migrations change the schema and
never the ciphertext in it — a broken key setting must not be able to block a
schema change. Each `cmd/*/config.go` is a complete answer to "what does this
process need to run?"

An unusable configuration stops the process. There is no degraded mode worth
having: a missing database URL is not something the application can work around,
and discovering it at the first request rather than at startup turns a
deployment mistake into an outage. Validation reports **every** problem at once,
as plain lines rather than a log record — nothing is running yet, and the reader
is a person looking at a container that would not start:

```
api cannot start.

  SECRETS_KEEPER_URL must not use base64key:// when APP_ENV=production; use a managed key service
  TEMPORAL_HOSTPORT is required
  TOKEN_SIGNING_KEY is the default published in this repository and is not permitted when APP_ENV=production
  APP_DB_PASSWORD is the value published in this repository; set a real one when APP_ENV=production
  APP_PUBLIC_URL must be https when APP_ENV=production
```

Five restarts collapsed into one fix.

### Shared resources are created once and handed down

Each binary opens the connection pool, the key service client and the outbound
HTTP client at startup, and passes them to whatever needs them. Nothing further
down constructs its own.

That is worth being strict about. A pool created in a corner is one nobody can
size, instrument or shut down, and two of them silently double a database's
connection count. The same applies to the HTTP client: it carries a connection
pool and a timeout, so the process should own exactly one and hand it to every
connector, rather than each package discovering its own defaults.

The API's `dependencies` struct makes the set explicit, and returns a single
release function that closes them in reverse order.

### Every write is a transaction

`store.InTx` is the only way a write reaches the database, and it opens a
transaction. Reads go through `store.Read`, which does not.

Some of those writes are single statements that PostgreSQL would make atomic
anyway. They are wrapped regardless, because "a write is a transaction" is a
rule a reader can verify by looking, whereas "this particular write happens to
be atomic" has to be re-derived for each one — and stops being true the moment
someone adds a second statement. Reads that do not span rows are not wrapped: a
transaction around a single `SELECT` buys nothing and costs a round trip.

### The application cannot change the schema

Migrations run as the database owner; the API and worker connect as
`identityhub_app`, which holds `SELECT`, `INSERT`, `UPDATE` and `DELETE` and
nothing else. No DDL, so an injection or a bug cannot drop a table, and no
ownership, so it cannot grant itself more. `UPDATE` and `DELETE` are further
revoked on `audit_events`, making the audit trail append-only for the
application.

This is deliberately a small boundary — one `CREATE ROLE` and a few `GRANT`s,
readable in one screen. An earlier version of this schema used PostgreSQL
Row-Level Security, which is a stronger control but needs a page of explanation
before it can be reviewed. See §4.

### Queries are SQL, generated into Go

Every query lives in `db/queries/*.sql` and is compiled by **sqlc** against the
schema in `db/migrations`. There is no hand-written SQL in Go, and no ORM.

The most important invariant in this codebase is *no query crosses an account
boundary*. That has to be readable, and it is: each query is a few lines of SQL
with its `where org_id = $1 and account_id = $2` visible, in a file a reviewer
can read end to end without following a query builder.

What generation adds beyond readability:

- **A query is checked against the real tables at build time.** A typo in a
  column name, or a rename that misses a caller, fails at `sqlc generate` rather
  than at the request that happens to hit it.
- **The parameters and the row are types.** Transposing two arguments of the
  same width — `org_id` and `account_id`, say — is a compile error rather than a
  query that silently returns the wrong tenancy.
- **`ListConnections` cannot accidentally select the ciphertext.** The column
  list is in the SQL, so a change to what a listing reads is a visible diff in a
  query file.

`internal/store` remains a thin layer over the generated code, doing the three
things the generator cannot: requiring a `Scope` on every call, running every
write in a transaction, and translating database errors into domain ones.

### Why the browser sees a single origin
The production image serves the built React app from `embed.FS` on the same origin as
the API. This removes CORS configuration entirely — including for the Swagger page, which
calls the same origin it was served from — and eliminates an entire class of "works
locally, breaks in Docker" bugs. Local development uses the Vite dev proxy to preserve hot reload.

## 2. Authentication — two distinct surfaces

The brief mixes two different auth problems. We keep them fully separate, with separate
tables, separate lifecycles and separate middleware.

### 2a. People (browser)

**Sign-in is implemented. It is also the one part of this design a real
deployment throws away, and that is the interesting bit.**

The brief asks for "User Login to the app + Logout" and "secure session
management". **What actually happens, end to end:**

- A person **signs in** with an email address and a password. The password is
  checked with bcrypt against a hash; nothing else is stored.
- On success this application **mints a token and signs it** (HMAC-SHA256). The
  token carries who they are, which organization and account they act in, what
  roles they hold, a unique id (`jti`), and an expiry.
- The browser keeps it in `sessionStorage` and sends it as
  `Authorization: Bearer …` on every request. **Every request verifies the
  signature first** — nothing in the token is trusted until it does.
- The token is good for **one hour**, and no longer. There is no refresh flow:
  renewing a credential is the identity provider's job, not ours.
- On **sign-out**, the token's `jti` goes into Redis with a TTL equal to what is
  left of its life. Every request checks that list, so **the token stops working
  everywhere at once** — including for anyone holding a copy of it. The record
  deletes itself when the token would have expired anyway.
- **In production none of the first two bullets is ours.** Auth0, Clerk or Okta
  authenticates the person and issues the token; everything from the third
  bullet onward is unchanged.

| | How |
|---|---|
| Login | `POST /api/auth/signin` — email and password, bcrypt, issues a signed token |
| Logout | `POST /api/auth/signout` — the token stops being accepted, immediately, for anyone holding a copy |
| Session management | Signed HMAC-SHA256, one hour, tenancy in the claims, revocable before expiry |

**What a real deployment changes, and what it does not.** Every organization
that would buy an NHI platform already has an identity provider, and asking it
to keep a second password *in a security product* is asking it to take on a
liability for our convenience. So in production this is Auth0, Clerk or Okta:
they authenticate the person and they issue the token.

What does not change is everything after that point. `auth.TokenResolver` is the
seam:

```go
type TokenResolver interface {
    Name() string
    Resolve(ctx context.Context, r *http.Request) (Claims, error)
}
```

Federating means writing one implementation that verifies an RS256 signature
against the provider's JWKS instead of an HS256 one against our own key, and
deleting `signin.go` and its endpoint. **Nothing downstream of `Claims` knows
which one produced it** — not a handler, not a query, not the audit trail.

**Tokens are signed, and the library does the signing.** `auth.Tokens` issues and
verifies with one key, because a design where minting and checking could
disagree about the key or the algorithm is a design with a hole in it.

The JWT work is `golang-jwt/jwt/v5`'s. An earlier version hand-rolled it — a page
of base64, HMAC and expiry arithmetic — and that was the wrong call: it is
exactly the code where a subtle mistake is invisible and expensive, a maintained
library already has it, and writing your own is not a thing to show a reviewer.

**What is ours is the configuration**, and that is where the security decisions
actually are:

```go
jwt.WithValidMethods([]string{jwt.SigningMethodHS256.Alg()})  // pinned, not read
jwt.WithExpirationRequired()                                  // exp is not optional here
jwt.WithLeeway(30 * time.Second)                              // clocks are never in step
jwt.WithIssuer(issuer) / jwt.WithAudience(audience)           // when configured
```

The first line is the one that matters. Without it the parser believes the
token's own header about how it was signed, which is a verifier a caller can talk
out of verifying: the `"alg": "none"` forgery, and the RS256-to-HS256 confusion
where an attacker signs with the public key. The library requires you to pin,
because not pinning caused real CVEs in JWT implementations generally.

`TestAForgedTokenIsRefused` drives five forgeries including both of those, and it
did not change when the library replaced the hand-rolled code — because it tests
this configuration, not the library.

**Two gaps the swap closed.** `aud` is now read as either a string or an array,
which RFC 7519 permits and real providers emit; the hand-rolled version read it
as a string and would have rejected a valid Auth0 token. And there is now clock
leeway, so a provider whose clock is a second ahead does not produce a sign-in
that fails for no reason a person can act on.

The signing key's default is published in this repository, so configuration
refuses it when `APP_ENV=production` — the same rule as the database password.
Anyone holding it can mint a token for any tenant, which is the whole point of
saying so.

**Passwords are bcrypt, and the contrast with the API key is deliberate.** Two
credentials, two hashes, opposite reasoning:

| | Password | API key |
|---|---|---|
| Entropy | Low, human-chosen | 256 bits from a CSPRNG |
| Attack | Offline dictionary | None available |
| Hash | bcrypt, with a work factor | SHA-256, plain |
| Why | Make each guess expensive | A work factor would cost latency on every request and buy nothing |

Same table, same word "hash", two different problems. Getting that backwards in
either direction is the mistake this pair exists to avoid.

**What sign-in deliberately does not have.** No lockout and no rate limiting on
failed attempts. It is a known gap rather than an oversight: doing it properly
means a counter per identity with a window, a threshold, a disable period and a
way to clear it — state, policy and an unlock path, all of which need product
decisions this exercise does not ask for. What *is* there is the cheap half: an
unknown address and a wrong password answer identically and take the same time,
because the lookup miss still pays bcrypt against a decoy hash. Without that,
response timing tells an attacker which addresses have accounts here.

**What happens if a token is stolen, and why we did not "bind it to a session".**

A bearer token is a bearer token: whoever holds it is the user, until it
expires. Three things bound that, and none of them is a guess:

- **One hour**, not a day.
- **Signing out kills the stolen copy too.** Revocation is by `jti`, not by
  browser, so the moment the real person signs out the thief's copy stops
  working in the same instant.
- **`sessionStorage` and a strict CSP.** The token dies with the tab, is not
  shared between tabs, never appears in a URL, and `default-src 'self'` closes
  the main exfiltration path.

The obvious next idea is to bind the token to something about the client, and we
rejected both cheap versions on the merits:

| | Why not |
|---|---|
| Bind to IP | Mobile networks re-address mid-session, VPNs and corporate NAT shift, ISPs renew leases. People would be signed out at random — and an attacker on the same café NAT passes anyway. High cost, low value. |
| Bind to User-Agent | Whoever stole the token stole it from a request containing the User-Agent. Forging it is free. It also breaks on every browser auto-update. Theatre. |
| One session per person | Real, and small — a second sign-in revokes the first. But it answers a different question: it stops two *logins*, not a stolen copy. Same `jti`, both requests pass. |

The two mechanisms that actually solve theft are both bigger than this exercise,
and both belong to the identity provider in a real deployment:

1. **Refresh-token rotation with reuse detection.** The refresh token is
   single-use; presenting it twice proves one of the two holders is a thief, and
   since you cannot tell which, you revoke the family and force
   re-authentication. This is what Auth0 and Clerk do, and it needs the refresh
   flow that is out of scope here.
2. **Sender-constrained tokens — DPoP (RFC 9449) or mTLS (RFC 8705).** The client
   holds a non-extractable key and signs every request with it, so the token
   stops being a bearer token: stealing it is worthless without the key. This is
   the real answer, and it is a project rather than a feature.

So the position is: **bounded, detectable, and not claimed to be more.** Claiming
IP-binding as a mitigation would be worse than claiming nothing, because it would
suggest a protection that a shared NAT defeats.

**What "logout" is here.** `POST /api/auth/signout`, and then the browser
discards its copy. Federating covers who issues a credential; it does not cover
when we stop accepting one, and that half is ours whoever issued it. A logout
that only cleared `sessionStorage` would not be one — a token copied out
beforehand never touched that storage and would keep working until it expired.

What it does **not** do is end the provider's session, because that is the
provider's to end. In a real deployment this is followed by an RP-initiated
logout redirect, which is one function and no schema.

**One key in Redis, and it is not a session store.**

```
SET identityhub:revoked-token:<jti> <subject> EX <seconds until the token expires>
```

A session store holds an entry per *active* session and is read to decide that a
caller **is** signed in — which is the state this design exists to avoid. This
holds an entry only for a token signed out while still valid, and is read to
decide that one is **no longer welcome**. Nothing is written when a person signs
in, and if the whole store were flushed, everyone would stay signed in rather
than be locked out. That inversion is the distinction.

**Why Redis rather than a table.** The record has exactly one property that
matters: it must live as long as the token would have, and then stop existing —
after which the token is refused for being expired anyway. That is a key with a
deadline, and expressing the deadline as the storage engine's own TTL removes
the question of who deletes it and when. In Postgres the same thing needs a
column, a sweep and a decision about when to run it. The second reason is where
the read happens: every authenticated request asks this question, so it belongs
on a lookup built for that rather than on a connection the request may not
otherwise need. Durability is not the concern it would be for a table — the data
is meant to be lost, and losing it costs at most the remaining lifetime of the
tokens signed out in the last hour.

What is durable lives in Postgres: `audit_events` records permanently that
somebody signed out, and which token. Redis holds only the enforcement.

**A cache to store in, not a cache to fall back from.** The package is
`internal/cache` because that is what Redis is here — keys with deadlines, whose
contents are meant to be lost. But nothing *falls back* from it: the set of
signed-out tokens exists nowhere else, so a process that cannot reach Redis
answers `503` and authenticates nobody rather than guessing. Being unable to tell
whether a credential was revoked is not a reason to honour it. `/readyz` reports
it for the same reason: a process that must refuse every request should not be
sent any.

Those two senses of "cache" are worth keeping apart, because conflating them is
how an optional-looking dependency ends up fail-open. An API key carries no
`jti` and is revoked through its own row instead.

**Two limits worth naming.** There is no idle timeout and no refresh flow —
token lifetime and renewal are the provider's side of the exchange, so an hour
absolute is the bound. And revocation is per token: there is no "sign out
everywhere", which needs either a way to enumerate a subject's live `jti` values
or a per-subject not-before timestamp on every request. Both are in §9.

### 2b. Machine access (public REST API)

The `api_keys` table holds IdentityHub's **own** API keys — the `ih_...`
credentials a scanner or CI pipeline presents to `POST /api/v1/findings`. It is
unrelated to the key service: nothing about KMS is stored there.

It has no column holding a key, deliberately. Only a SHA-256 hash of the secret
is stored, the full key is displayed once at creation, and it is not recoverable
afterwards — which is the point of the table rather than an omission from it.
- API keys formatted `ih_<key_id>_<secret>`; only a SHA-256 hash of the secret is
  stored, and the full key is displayed exactly once at creation.
- Keys are **tenant-scoped**, carry `last_used_at`, and can be revoked independently.
- Presented via `Authorization: Bearer`, compared in constant time.

### Every outbound call has a deadline, and they are not the same deadline

A call with no ceiling is a parked goroutine and an occupied connection. So every
one has a budget, and the budgets differ because what they are waiting for
differs:

| Call | Budget | Why that number |
|---|---|---|
| Revocation check (Redis) | **250 ms** | On the hot path of every authenticated request. A local lookup that has not answered by then has failed. |
| Connecting to Redis at startup | **30 s** | Not serving yet, and a managed Redis or a container ordering race can take that. Refusing to boot on a slow first connection is the worse failure. |
| Live ticket status | **3 s** | Decoration: the recent-tickets list renders from our own records either way, so it must not hold the page. |
| Readiness probe, per dependency | **2 s each** | Each gets its own, not a share of one — a hanging check must not make its neighbours look unavailable too. |
| Outbound provider call | **20 s** | Somebody else's API over the internet, on a path a person is waiting on. |
| Synchronous wait for a filing workflow | **8 s** | Then `202` and the ticket appears in the list. Bounded so a slow provider does not hold a request. |
| Release of an idempotency claim | **10 s**, 3 attempts | Cleanup on a path that has already failed. |

Two of these are worth the detail, because they were wrong first:

**A per-call context is not enough for a pooled client.** With a blackholed
Redis, a 250 ms `context.WithTimeout` still produced a **5-second** request — the
deadline was honoured, but `go-redis` spends its own budget getting a usable
connection out of the pool *before* the command sees the caller's context. The
fix is to bound the client where it is built (`DialTimeout`, `ReadTimeout`,
`PoolTimeout`, `MaxRetries`), the same argument as `connector.NewHTTPClient`: a
shared client is sized once, by the process that owns it. Measured after:
**0.26 s**.

There is nothing to fall back to when Redis does not answer, so the budget above
is a failure deadline rather than a retry window. §2a has the reasoning; this
number is what keeps the failure survivable.

### The linter's opinion counts, and where it does not, it says why

`make lint` used to end in `golangci-lint run ./... || true`, which discarded the
result. Removing that revealed twelve findings, ten of which were fixed. The
other two are turned off in `.golangci.yml` **with the reason written next to
them**, because a suppression without a reason is indistinguishable from one
added to make a build green:

- **ST1005** wants error strings lowercase and unpunctuated. Right for errors that
  a caller wraps into a sentence; wrong here, because these errors *are* the
  sentence — an error declared in this application carries the text the API
  returns and a person reads, and nothing rewrites it on the way out.
- **S1016** wants a type conversion where two structs have identical fields. In
  `jira/issuetracker.go` they are identical by coincidence and separate by
  design: one set is Jira's model, the other is the contract's shapes, and that
  file exists to translate between them. A conversion would hide that there are
  two vocabularies.

### Which tests run in parallel

`t.Parallel()` is not sprinkled; it follows one rule. A test that needs no
infrastructure declares it, and a test that touches PostgreSQL, Redis, KMS,
Temporal or a live Atlassian site does not — those share one database and one
namespace, and interleaving them would make ordering a property of the
scheduler. The one further exception is a test using `t.Setenv`, which cannot
also be parallel: an environment variable is process-wide, so a parallel test
cannot own one.

The whole suite runs clean under `-race`.

## 3. Connectors and stored credentials

### The connector package is infrastructure, not domain

This is the boundary that matters, and it took two attempts to get right.

`internal/connector` knows how a connector is **identified, configured,
dispatched, and how its failures are classified**. It knows nothing about what
any connector does. Its entire dependency list is the standard library.

Everything provider-shaped lives in the provider's own package:

| Lives in `connector` | Lives in `jira` (and would live in `github`, `okta`, …) |
|---|---|
| `Type`, `Action`, `Request`, `Response` | `Action` constants, `parseAction` |
| `Connector`, `Config` interfaces | `Config` struct, its validation |
| `Registry`, `StrictDecode`, `EncodeConfig`, `Supports` | `Project`, `Issue`, `IssueType`, `Account` |
| Error classification (`ErrUnauthorized`, `ErrRateLimited`, …) | `CreateIssueParams`, `GetIssuesParams`, … |
| | Typed methods: `CreateIssue`, `ListProjects`, `GetIssues` |

An earlier version kept `CreateIssueParams`, `Issue` and `Project` in the shared
package, as "the data contract". That was wrong: Jira has issues and projects,
GitHub has repositories and pull requests, Okta has applications and grants. A
shared type covering three domains becomes either a union nobody fully
implements or a Jira model wearing a generic name — and every new integration
gets pushed to describe itself in the first connector's vocabulary.

The error classes are the deliberate exception, and they earn it: any
credentialed HTTP API can reject a credential, refuse a permission, rate limit,
or fall over. Those classes are properties of *talking to a remote service*,
not of any provider's model, and callers genuinely need to act on them
uniformly — the HTTP layer to pick a status code, a Temporal activity to decide
whether to retry.

**The invariant is structurally enforced.** Every connector imports
`connector`, so Go's import cycle rule makes the reverse impossible. There is no
way for a provider's model to migrate into the shared package by accident.

### One interface, uniform for every connector

```go
type Connector interface {
    Type() Type
    DecodeConfig(plaintext []byte) (Config, error)
    Actions() []Action
    Requirements() Requirements
    Execute(ctx context.Context, cfg Config, req Request) (Response, error)
}
```

Nothing Jira-specific appears — not the methods, not the actions. `Requirements`
is the exception that proves the rule: it describes what a connector needs to be
configured, which has to be answerable *before* any configuration exists, so it
cannot live behind `Execute`.

Nothing above this package branches on connector type. There is one call site in
the whole application:

```go
res, err := c.Connector.Execute(ctx, c.Config, connector.Request{Action: action, Params: encoded})
```

**One way in, and only one.** An earlier version had two: `Execute` for callers
that could not link Go types, and a `Tracker` interface reached by a type switch
for callers that could. Both worked. That was the problem — a
reviewer asking "where does connector #2 plug in?" got two different answers, and
this document described the one with no callers. A seam that is *sometimes* the
seam is not a seam.

**The contract is JSON, not a Go interface.** Because `Execute` carries opaque
payloads, the issue-tracker capability is five action names and the shapes that
go with them, written out in `internal/capabilities/issuetracker`:

```
verify_credentials  {}                              -> Owner
list_targets        {query, limit}                  -> []Target
list_kinds          {targetKey}                     -> []Kind
file_ticket         {targetKey, kindId, title,      -> TicketRef
                     description, labels}
fetch_tickets       {keys}                          -> []TicketRef
```

Both sides declare their own structs and agree on the tags, so `jira` does not
import `issuetracker` and `issuetracker` does not import `jira`. Jira's model
stays Jira's — projects and issue types, not targets and kinds — and the
translation lives in `jira/issuetracker.go`, the only file in that package that
knows the contract exists. Nothing makes the two struct sets agree at compile
time, so `jira/issuetracker_test.go` does: it round-trips the product's own types
through `Execute`, and a renamed field fails there rather than in production.

**Three packages, one direction.** The layering is visible in the import graph,
which is the only claim here that cannot be argued with:

```
capabilities/issuetracker  ->  connector
connections                ->  connector  capabilities/issuetracker  crypto  store
connector                  ->  (nothing of ours)
connector/jira             ->  connector
```

`connector` is the port. `capabilities/issuetracker` is what this product asks
for over it — one capability a connector may or may not have, which is why it is
not five more constants inside `connector`. `connections` is where an account's
credential is stored, decrypted and paired with a connector; it is the only
package in the application that decrypts anything, and the only reason it exists
is that a connector must not know which database or key service we run.

An earlier version had one `findings` package holding all three jobs. It was
named after the payload rather than the work, and a reader had to open it to
find out what it did.

Adding a connector means implementing `connector.Connector`, registering it, and
implementing those five actions. No workflow, activity or handler changes.

**Two smaller properties that follow.** `DecodeConfig` is a method rather than a
shared function, because only the connector knows what its fields are and what
makes them valid — what *is* shared is `StrictDecode`, the checks that make any
decode safe. And implementations are **stateless**: a configuration is passed to
each call rather than held, so one registered instance serves every account and a
credential lives no longer than the call that needs it.

`Requirements()` is what makes the connect form generic: Jira reports a site, an
email and a token, a GitHub connector would report one token, and
`GET /api/connections` returns whichever — so the form is built from the response
rather than written for one provider.

### Actions belong to the connector that implements them

The `connector` package declares the `Action` *type* and no constants. Each
connector defines its own set:

```go
// package jira
type Action connector.Action

const (
    ActionVerifyCredentials Action = "verify_credentials"
    ActionFileTicket        Action = "file_ticket"
    // ...
)
```

A central list would grow to the union of every connector's operations while no
single connector implements all of them, and every new integration would edit a
shared file.

`Execute` begins with `parseAction`, which converts the incoming action into the
local type **and checks membership** — the conversion alone always compiles, so
the membership check is what makes it a real cast. `allActions` is the single
source of truth for both `Actions()` and `parseAction`, so the declared set and
the accepted set cannot drift.

### The cost of an action-keyed interface, and how it is paid

`Execute(action, params)` trades compile-time safety for uniformity. That trade
is the obvious objection, and it is paid back four ways:

1. **`Action` and `Type` are named types**, not bare strings, so a typo in
   connector code is a compile error.
2. **Order of checks.** The action is resolved *before* the configuration is
   touched, so an unsupported request never reaches a credential. There is a
   test for exactly that.
3. **Declared and dispatched sets cannot diverge.** A test asserts every action
   `Actions()` reports is handled by `Execute`, and `parseAction` rejects
   everything else. The `default:` branch in the dispatch switch is unreachable
   by construction and exists so that adding a constant without a branch fails
   loudly rather than returning an empty response.
4. **Typed methods exist, but they are the connector's own.** `jira` declares
   `CreateIssue`, `ListProjects`, `GetIssues` and their parameter types, and
   `Execute` dispatches to them -- one implementation behind both, so they
   cannot drift. What changed in the rework is who calls them: **application
   code does not.** It goes through `issuetracker.Client`, which is `Execute`
   with the product's vocabulary on top, and pays a marshal and an unmarshal
   for it.

   Application code does not call them — it goes through `issuetracker.Client`,
   and pays a marshal and an unmarshal for the uniformity.

Because parameters and results are the connector's own types, the generic layer
carries them as opaque JSON. That is the point rather than a workaround: a
Temporal activity moves a payload from a workflow to a connector without either
knowing what is inside it, which is what lets a new connector arrive without
editing shared code.

### The connections table is generic

There is no `jira_connections` table. A table named after one provider bakes
that provider into the schema, and the second connector arrives as either a
second table or a migration.

One `connections` table serves every connector type. A row names its
`connector_type`, and the connector-specific configuration is stored as an
**encrypted blob whose plaintext is JSON**.

The configuration is deliberately *not* a plain `jsonb` column: it contains the
credential, and a credential must not be readable by anyone who can read the
table. Non-secret fields — site URL, account email — live in a separate
`metadata jsonb` column instead, so listing connections for the UI needs no
decryption and no key service round-trip at all.

### Resolve, check, decrypt, decode — in that order

`connections.Configure` is the only path from a stored row to something callable,
and its order is deliberate on two counts:

1. **read the row**, scoped to the account, so a connection is only ever found
   for its own tenancy;
2. **resolve the connector** — cheap, and it cannot fail for any reason involving
   the credential;
3. **check the capability** — does this connector implement the issue-tracker
   contract at all;
4. **decrypt** — last, so a credential is only in memory when there is something
   to do with it;
5. **decode** into the connector's own type, which is its job because only it
   knows its fields.

The decrypt used to come second, and a test written for a different reason caught
what that costs: a stored connection whose type this build no longer has failed
with *"The stored credential could not be decrypted."* That is the wrong sentence
— it sends somebody to reconnect a credential that is fine. Resolving first makes
it *"IdentityHub does not have a github connector"*, and as a side effect a
credential that is not going to be used is never decrypted at all.

Decryption succeeding proves only that the bytes are ours. It does not prove
they are the right *shape*: a row could predate a schema change, or belong to a
different connector. `StrictDecode` therefore runs a fixed sequence:

1. reject an empty or oversized blob,
2. decode with `DisallowUnknownFields` — a blob that does not match the struct
   is more likely to be another connector's data than a harmless extra field,
3. reject trailing data,
4. run the configuration's own `Validate()`,

and the connector's own `DecodeConfig` is the only thing that runs it. There is
no path from stored bytes to a usable configuration that skips this — the
registry resolves a type and the connector decodes its own bytes, two steps
because they are two different jobs.

Parse errors are not wrapped, because `encoding/json` quotes the offending input
and that input is a credential. A test asserts the token never appears in an
error message.

One tradeoff worth recording: `DisallowUnknownFields` means that *removing* a
field from a config struct breaks previously stored rows. That is the right side
to err on here, but it is a deliberate strictness rather than a free win.

### Validation uses the standard library, not string matching

`Config.Validate` checks the account email with **`net/mail.ParseAddress`**
(RFC 5322) and the site URL with `net/url.Parse`. An earlier version tested for
an `"@"`, which both accepts addresses Jira rejects and rejects addresses Jira
accepts. A test exercises the standard's edge cases — quoted local parts,
display-name form, plus-addressing — against the implementation.

The site URL must be an `https` origin with no path, query, fragment or embedded
credentials. The credential travels on every request, so plaintext transport is
refused outright.

### The Jira API client

Atlassian publishes **no official Go SDK**. The two community options are
`andygrunwald/go-jira` (v1 stable, v2 unstable) and
[`ctreminiom/go-atlassian`](https://github.com/ctreminiom/go-atlassian), which
is actively maintained and Cloud-focused. This project uses the latter.

An earlier version hand-wrote the HTTP client, the endpoint definitions and an
Atlassian Document Format builder. That is re-implementing a maintained library,
and it is hard to defend when asked "did you check whether one exists?" The
library also independently makes the two non-obvious endpoint choices this
project had to research — `createmeta/{projectKey}/issuetypes` and
`/search/jql` — which is a useful corroboration rather than a coincidence.

**What is still ours**, and deliberately so: the classification of upstream
failures. The library collapses several statuses into one sentinel — 403, 429
and 503 all arrive as `ErrInvalidStatusCode` — so the response code is the only
reliable signal, and that distinction decides both the HTTP status the API
returns and whether a Temporal activity retries or fails fast. Upstream text is
summarised rather than forwarded, since Atlassian error bodies can name internal
field IDs and workspace configuration.

Issue lookups use `BulkFetch`, which resolves issues by key without JQL at all —
cheaper than a search and it removes the injection surface entirely. Keys are
still shape-validated before being sent.

### Jira authentication

**Shipped: API token (Atlassian email + token, HTTP Basic).**
**Designed for: OAuth 2.0 3LO**, which go-atlassian also supports.

A deliberate trade-off against "runnable in the easiest, most frictionless way
possible": 3LO requires the reviewer to register their own app in the Atlassian
developer console and configure a callback URL before the application does
anything. The API-token path is a 30-second setup and — usefully — produces a
real long-lived secret, which is precisely the asset the credential-management
design exists to protect. In production, 3LO is the correct default, and a
static API token is exactly the finding IdentityHub would raise about itself.

### Scopes requested

Three classic scopes — `read:jira-user`, `read:jira-work`, `write:jira-work` —
covering exactly the five endpoints this product calls and nothing else. Nothing
edits, transitions, deletes or comments on an issue.

The granular equivalent for the same five calls is 22 scopes, and it is
genuinely narrower: `write:jira-work` grants every write in Jira, whereas
`write:issue:jira` grants writes to issues. A longer list of narrow scopes is
less access than a short list of broad ones. It was still not the choice here,
for two reasons: Atlassian marks the granular scopes **Beta** while the classic
three are **Current**, and a 22-line scope list is one nobody checks — least
privilege in appearance rather than in fact. If those scopes were GA, the answer
would flip.

Worth naming as a limit: `write:issue:jira` does not stand alone. Atlassian
bundles `write:comment:jira` and `write:attachment:jira` with the create-issue
endpoint, because that endpoint can create both in one call. We use neither. So
least privilege is bounded by how a provider chose to slice its scopes, not only
by what the client calls.

The per-endpoint mapping, the setup walkthrough and the troubleshooting table
are in [CONNECTING-JIRA.md](CONNECTING-JIRA.md).

## 4. Multi-tenancy

Tenancy is two layers deep, because one layer is not multi-tenancy:

```
organization   a customer
   └─ account  an isolated workspace; one organization may have many
        └─ user
```

The **account** is the unit of isolation. Every tenant-owned table carries both
`org_id` and `account_id`, and every query filters on both. Nothing is scoped by
organization alone — two accounts inside one customer are as isolated from each
other as two different customers.

### How it is enforced

1. **Identity.** Every session and API key resolves to a scope in middleware. A
   handler never assembles a scope from user input.
2. **A required argument, checked once at the top.** A `store.Scope` is built in
   middleware from the credential's claims and validated there —
   `Scope.Validate` refuses a nil organization or account, so a half-empty
   tenancy fails at the boundary rather than reaching a query.

   Being exact about what this does *not* do: below that boundary the generated
   parameters are two `uuid.UUID` fields, and nothing stops a caller passing them
   in the wrong order. What makes that safe is not a type but the identifier
   space — organization and account ids are distinct random UUIDs, so a
   transposition matches no row and fails closed. It is a weaker guarantee than a
   compile error, and it is the honest one.
3. **The SQL itself.** Every statement carries `where org_id = $1 and
   account_id = $2`.

### Why not PostgreSQL Row-Level Security

An earlier version of this schema used RLS: a database policy that appends a
tenant predicate to every query automatically, catching the case where someone
adds a query later and forgets to scope it.

It was removed, deliberately. RLS is a real safety net, but it is not free:
turning it on means login can no longer read `users` to discover which account
an email belongs to — the tenancy is the *result* of that lookup, not an input
to it — so three bootstrap paths need `SECURITY DEFINER` functions, which in
turn need a dedicated `BYPASSRLS` role that is the only privilege escalation in
the system. That is a lot of database machinery standing between a reader and
the answer to "how is this isolated?"

The scoping rule here is legible from the Go code alone. The invariant is one
type and one helper, both of which fit on a screen. That is worth more than an
invisible backstop, especially in a codebase whose isolation properties are
meant to be reviewed.

**What replaced the safety net.** Rejecting RLS gives away the forgotten-`WHERE`
net, and it is worth being exact about what that means, because the obvious
substitute does not exist: **no SQL constraint can require that a query filters
on a column.** `NOT NULL`, `CHECK` and foreign keys govern data at rest --
`org_id` and `account_id` are already `NOT NULL` with foreign keys, and
`select * from tickets` still returns every tenant's rows. RLS is the only
database mechanism that forces a predicate onto a query, which is precisely the
thing being declined here.

So the net is rebuilt one layer up, where this design argues the decisions
belong. `TestEveryTenantOwnedQueryFiltersOnBothHalves` reads `db/queries/*.sql`,
finds every statement touching a tenant-owned table, and fails the build unless
it constrains **both** halves -- in the `WHERE` for a read, update or delete, and
in the column list for an insert. A query that filters on `org_id` alone does not
reach a review; it does not reach a merge.

The three queries that are deliberately unscoped are listed in that test with the
reason each one is allowed to be: signing in and API key authentication both
*discover* a tenancy rather than receive one, and `TouchUser` acts on a primary
key that a scoped read already resolved. A list rather than a pattern, because
every entry is a decision, and the map is the complete set of places the
invariant does not hold.

It found one on its first run: `ListAllUsers`, a cross-tenant read of every
person in every organization, left behind when the development identities
endpoint was deleted and surviving only for a test harness. It has been removed,
and the harness now looks people up through the same scoped query signing in
uses.

Three properties are now distinct, and conflating them is the mistake this guard
exists to prevent:

| Question | Answered by |
|---|---|
| Is a tenancy present and complete? | `Scope.Validate`, in middleware, from the token's claims |
| Does every query use both halves of it? | The static check above, at build time |
| Do two real accounts stay invisible to each other? | The isolation tests below, against a real database |

### Tested, not asserted

`internal/store/scope_test.go` runs against a real PostgreSQL instance and
asserts that:

- two accounts **inside the same organization** cannot see each other's data —
  the case a single-layer tenancy check would miss,
- two organizations cannot see each other's data,
- a scope missing either half is rejected rather than treated as a wildcard,
- a scope mixing one account's `org_id` with another's `account_id` matches
  nothing, rather than falling back to either column alone,
- a connection listing never loads the encrypted configuration, and a
  serialised connection never contains its ciphertext.

Encryption is bound to the same scope: `org_id/account_id` is written into the
plaintext before it is encrypted, and checked after decryption, so a ciphertext
moved between sibling accounts comes back unusable rather than merely
unauthorized. §5 has the mechanism and why it is not AES-GCM additional
authenticated data.

## 5. Credential encryption

A connector configuration is encrypted by a key service and stored as one blob.

```
connections
  config_encrypted  bytea   the configuration, encrypted
```

The key service is reached through the **Go CDK** (`gocloud.dev/secrets`), so
the provider is a URL and switching it is configuration:

| Scheme | Use |
|---|---|
| `awskms://` | Default. Locally this is [floci](https://github.com/floci-io/floci), an emulator speaking the real KMS protocol with no account and no auth token; in production, AWS KMS. The application code is identical — only `AWS_ENDPOINT_URL` differs. |
| `base64key://` | Offline fallback for tests. Refused when `APP_ENV=production`. |
| `gcpkms://`, `azurekeyvault://`, `hashivault://` | Available by adding one import line. |

### Why there is no envelope, and where the nonce went

An earlier version did envelope encryption: generate a data key per credential,
wrap it with the key service, and store the wrapped key, a nonce and the
ciphertext in three columns.

That is the right shape for large payloads — it avoids pushing megabytes through
a key service with a small request limit. A connector configuration is about
**300 bytes**, and AWS KMS accepts **4 KB**. So the payload goes to the key
service directly and one blob comes back, which removed a data key, a nonce, two
columns and the code that kept them consistent, for no loss: the same key
service protects the same secret, in the same number of round trips.

The nonce did not stop being necessary. AES-GCM requires one, and reusing a
nonce under a single key is catastrophic — it reveals the XOR of two plaintexts
and enables forgery. What changed is *who owns it*: the provider now generates
it and carries it inside its own ciphertext, which is a better place for it than
a column this schema has to get right.

### The column that recorded the key, and why it went

There was an `encryption_key` column holding `awskms:alias/identityhub`, so that
a deployment which rotates keys could tell what decrypts an existing row. It was
written on every insert and read by nothing, and the reasoning behind it was
wrong: **a KMS ciphertext already carries the ARN of the key that produced it**,
and the providers that do need telling take the key from the keeper URL the
process was configured with. The column recorded something the ciphertext
already knew, which is why it was removed rather than wired up.

The same trim reached the package. `crypto` is `OpenKeeper`, `Encrypt`,
`Decrypt` and nothing else — no `Sealer` type, because a struct whose only field
is the key service client adds a name and no behaviour.

### The scope is inside the ciphertext

`gocloud.dev/secrets` exposes no additional-authenticated-data parameter, so the
tenancy scope is prefixed into the plaintext before encryption and checked after
decryption. A row copied between accounts fails to decrypt rather than silently
succeeding, and a test asserts that in both directions.

## 6. "Recent tickets created from this app"

The brief asks for the 10 most recent tickets *created from this app*, which is a
narrower set than "recent tickets in the project". We therefore record every created
issue locally (`tickets`: tenant, actor, project key, issue key, summary, source,
timestamps) and treat that table as the source of truth for the list.

**Why not a Jira label + JQL.** A label (`nhi-identityhub`) is mutable by any Jira user
and can be added to issues we did not create or stripped from ones we did. It cannot
answer "created from this app" reliably. We still *apply* the label for traceability
inside Jira, but we do not *trust* it for the query.

Live fields (current status, whether the issue was deleted in Jira) are hydrated with a
single bulk JQL `issue in (...)` call, so the view stays accurate without N+1 requests.

## 7. Public REST API

`POST /api/v1/findings` — creates an NHI finding ticket.

- **REST conventions**: `201 Created` with a `Location` header and the created resource.
- **API key required**: `Authorization: Bearer ih_...`, tenant-scoped.
- **Validation**: field-level. Every response is one envelope — `data` on success,
  `error` on failure — and `error.fields` names each bad input, keyed by the field
  in the request, rather than a single opaque string.
- **Status codes**: `400` malformed, `401` missing/invalid key, `403` key lacks
  scope, `404` unknown project or ticket, `409` not connected / credential
  rejected / idempotency conflict, `422` semantically invalid, `502` for upstream
  Jira failures and `503` when Jira rate limits or the durable queue is
  unavailable. Never masked as `500`: a `500` in this API means an error nobody
  classified, and it is logged with the request ID rather than described.
- **`Idempotency-Key` header**: a scanner or CI pipeline that retries on timeout must
  not create duplicate tickets. The key is stored per tenant with the resulting issue
  key; a replay returns the original ticket with `200` and `created: false` rather
  than filing a second one. A replay is a success, not a conflict — the caller asked
  for the finding to exist, and it does — so the body says which of the two happened
  and a client need not branch on the status code to find out.

  **What this does not cover, deliberately.** The key is claimed once per workflow.
  If the Jira call succeeds and its *response* is lost, Temporal retries the activity
  inside that same execution, below the claim, and Jira gets a second create. The fix
  is search-before-create on retry, keyed on a marker label unique to the execution —
  which narrows the window rather than closing it, because Jira's search index is
  eventually consistent and Jira offers no idempotency token of its own. It is not
  built: the window is a lost response on an already-successful call, and the machinery
  to half-close it costs more than the failure it prevents at this scale. Named here so
  it is a decision rather than an omission.

Upstream Jira errors are translated, not proxied: a raw Atlassian error body is not a
useful message for a CI pipeline, and may leak workspace detail.

### The OpenAPI document is the source of truth, in three different senses

`api/openapi.yaml` is not a description of the API written alongside it. Being
exact about which parts it actually governs is the point, because "source of
truth" is easy to claim and easy to be wrong about:

| | How |
|---|---|
| **Routing** | Generated. `oapi-codegen` emits a `ServerInterface`, and an operation in the document with no method on the `Server` **does not compile**. |
| **Authorization** | Read at startup, not generated. `Server.guards()` walks the document's `security` sections and builds each operation's middleware from them; an unknown scheme or role **stops the process from booting**. |
| **Shapes** | Checked at test time. Every response the end-to-end suite receives is validated against the document with `openapi3filter`, so a field renamed in a handler and not in the document **fails the build**. |

The third was the last one added, and it is the one that closes the gap the other
two leave. Before it, handlers answered with their own structs and nothing
compared them to the document — the shapes agreed by hand and could stop agreeing
silently. Now a rename produces:

```
POST /api/tickets answered 201 in a shape the document does not describe:
  Error at "/created": property "created" is missing
```

The document is also loaded from `api.Spec` rather than from the copy
`oapi-codegen` embeds, so **the bytes that decide policy are the bytes served at
`/openapi.yaml`**. The published contract and the enforced one cannot be
different documents.

**Reading the document requires signing in.** `/openapi.yaml` carries the same
guard as the rest of `/api`, and the Swagger page asks for an email and password
before it fetches anything. The document is a complete map of an API that manages
credentials — every endpoint, every field, every constraint, and which operations
need which credential — and there is no reason for that to be readable by anyone
who has not been given an account. A customer's own engineers are who it is for.

The guard is applied in Go rather than in the document's own `security` section,
because that route is not one of the document's operations: it is how the
document is fetched, and a spec cannot describe its own delivery.

The sign-in form lives on the page rather than as a guard on the HTML for a
reason worth knowing: **a top-level browser navigation cannot carry an
`Authorization` header.** Gating the page itself would need a cookie, and this
application deliberately has none — which is also what makes it CSRF-immune. So
the shell is public and empty, and the thing worth protecting is protected. As a
side effect the token from signing in is applied to Swagger automatically, so
"Try it out" works on the first click with nothing to copy.

**What this does not do:** there is no request validator. The spec's `minLength`,
`maximum` and `pattern` constraints are documentation — they tell a client what
to send and they are what Swagger renders — and `internal/httpapi/validate.go` is
the enforcement. Two copies kept in step by hand. Wiring
`middleware.OapiRequestValidator` would collapse them into one, and is about four
lines; it is not done because the hand-written layer produces field-level errors
in this API's own envelope, and the generic validator does not.

## 8. Durable execution with Temporal

Two operations in this system are multi-step, cross a network boundary we do not
control, and are worse than useless if they half-complete. Those two run as
Temporal workflows. Nothing else does.

### What runs as a workflow, and what deliberately does not

| Operation | Durable? | Reasoning |
|---|---|---|
| Create finding ticket | **Yes** | Resolve project → resolve issue type → create in Jira → record locally → audit. A crash between steps 3 and 4 leaves an issue in Jira that the recent-tickets view would never show. |
| Blog digest | **Yes** | A recurring job with retries, dedup and a 24-hour cadence. This is what Temporal Schedules are for. |
| Recent tickets view | **No** | A read against our own Postgres. No partial failure to recover from, no durability requirement, and nothing to replay. Wrapping a `SELECT` in a workflow adds a round-trip and buys nothing. |

The last row is the deliberate one. Temporal is easy to over-apply, and using it
for reads would undercut the credibility of the two places it genuinely earns
its keep.

### Retries are bounded, including the ones that are allowed to fail

Two steps in the filing workflow are best effort: releasing the caller's
idempotency key when the work failed, and writing the audit event that says it
failed. Neither may fail the workflow — losing an audit line is bad, and failing
a filing over it is worse.

**"Best effort" has to mean *bounded* effort, and Temporal's default is not.** An
activity with no `RetryPolicy` gets `MaximumAttempts: 0`, which is unlimited. So
both steps were allowed to retry forever, and the order they run in made that a
real hazard rather than a theoretical one:

```
FileTicketUpstream fails
  → auditFilingFailure   ← retries forever if the audit write keeps failing
  → releaseClaim         ← never reached
```

The caller's `Idempotency-Key` would stay claimed permanently, and every replay
of it would get `409` for good — **exactly the lock-out `releaseClaim` exists to
prevent.** Both now share one policy with a ceiling on attempts and on total
time, and `TestAFailingAuditStillReleasesTheIdempotencyKey` drives a permanently
failing audit and asserts the key is still released.

### One failure is one audit event, not one per attempt

`audit_events` has `UPDATE` and `DELETE` revoked from the application role, so
anything written there is permanent. The failure audit used to be written inside
`FileTicketUpstream`, which retries up to five times — so one Jira outage put
**five `ticket.failed` rows** in front of whoever read the trail, and nothing
could tidy them.

The activity cannot fix this itself: it runs up to five times and every attempt
looks identical from the inside. **Only the workflow knows an attempt was the
last one**, so the audit moved there, as its own activity. `RecordTicket` already
guarded its own write for the same reason — a converging retry is one action, not
five — and this is the same rule applied to the failure path.

### Credentials never enter workflow history

**Temporal persists workflow arguments and activity results in its own
datastore.** Passing a decrypted Jira token as a workflow argument — or
returning one from an activity — would write a plaintext tenant credential into
a second system, with a different backup, retention and access model than our
own, where it would sit for the history retention period.

The rule this codebase enforces is therefore: **workflows carry `orgId` and `accountId`,
never credentials.** Decryption happens inside the activity that makes the Jira
call, and the plaintext crosses no activity boundary in either direction. For a
product whose subject is non-human identity, "we considered where the secret
goes when the orchestrator checkpoints" is the point, not a detail.

The related constraint is determinism: every Jira call, database write, LLM
request and HTTP fetch lives in an activity. Workflow code only decides.

### Ticket creation stays synchronous for the user

Making creation durable must not make it feel asynchronous. The brief requires a
clickable link through to the created issue, and "queued" is a worse product
than "Created NHI-123".

The API therefore starts the workflow and waits on its result under a short
deadline. Under the deadline it returns `201` with the issue key, exactly as a
non-durable implementation would. Over it, it returns `202 Accepted` with a
status URL and the workflow keeps retrying in the background. Durability is paid
for only in the rare slow path.

### Why this suits the problem domain

An NHI platform performs automated actions against customer systems. Being able
to show exactly what was attempted, what failed, what was retried and what the
inputs were — and to replay it deterministically — is an audit property, not
just an engineering convenience. It complements the `audit_events` table: the
table records what we decided, Temporal records how it was carried out.

### Two workers on one task queue

Found while testing, and worth recording because it will happen to anyone
running this: a worker left over from an earlier run kept polling the same task
queue and picked up tasks the newly built worker should have handled. Because it
was an older binary, those tasks failed in ways the current code does not.

That is a real property of the model rather than a local accident — a task queue
is a shared work pool, and a worker joining it is trusted to be current.
Production answers this with Temporal's worker versioning, which pins a workflow
to a build ID so that an old worker cannot pick up new work. That is beyond
scope here, but the failure mode is worth knowing: if a workflow fails in a way
the code does not explain, check what else is polling the queue.

### Deployment

The Compose stack runs the Temporal dev server: server, UI and SQLite
persistence in one container. Production would run the full server against
Postgres; the workflow, activity and client code are identical either way. The
container runs as root because the image's uid 1000 cannot write to a fresh
named volume — a dev-only concession, noted so it is not mistaken for a pattern.

## 8b. Bonus — NHI Blog Digest

A Temporal Schedule per Jira connection, `blog-digest/{orgId}/{accountId}/{connectorType}`, created when
a tenant connects Jira and deleted when they disconnect. It runs every 24 hours,
fetches the most recent posts from the Oasis blog, skips any already in the
`blog_posts` catalogue, summarizes the rest, and files one ticket each.

Deduplication is keyed on the post URL, which is stable across feed re-orderings
and title edits in a way a feed position or title hash would not be. The unique
index on `(org_id, account_id, post_url)` is the real guarantee: a replayed or concurrent
workflow attempting a second insert is rejected by the database rather than by
application logic.

The final activity files the ticket the same way the interface does — through
`issuetracker.Client`, in process — rather than by calling this application's own
public REST API over HTTP.

An earlier plan was the opposite, on the argument that self-calling would
exercise the API key path end to end and prove the endpoint works for external
systems. It was dropped, and the reasoning is worth recording because the
rejected version sounds better than it is: it would mean the worker holding an
API key it had to be issued and rotated, a network hop between two processes
that already share a database, and a scheduled job whose failure mode includes
"the API was briefly down" — all to test a path the end-to-end suite already
covers directly with a real key. The digest is an internal caller, so it uses the
internal path; `TestPublicAPIAndIdempotency` is what demonstrates the public one.

Summarization sits behind a `workflows.Summarizer` port — declared at the
consumer, not the implementation, which is the same rule §3 applies to
connectors — with three
implementations: **Claude**, **OpenAI**, and an offline summarizer.

All three share one prompt and one set of bounds, so a summary reads the same
whichever produced it and changing provider is not a change of behaviour.
`SUMMARIZER_PROVIDER` selects one; `auto` takes whichever API key is configured
and falls back to offline when neither is. That fallback is the point: the
digest is a bonus feature and must not be the reason the stack fails to start
for someone with no model account.

Two providers rather than one because which model a deployment may use is
usually a procurement decision rather than an engineering one, and the port
makes that a configuration line instead of a rewrite.

## 8c. The interface

React with Vite and Tailwind, TanStack Query for server state, and a small set
of hand-written components rather than a component library pulled in whole.

### What the interface is for

The brief grades product thinking, and the product is a security tool. That
shaped three things:

**Errors say what to do.** The API distinguishes a rejected credential from a
missing permission from an upstream outage, and writes a message for each. The
interface renders that message rather than substituting a generic one, and
attaches field-level rejections to the fields they name. "Something went wrong"
appears nowhere.

**Provenance is visible.** Every ticket shows whether a person filed it, a
scanner filed it through the API, or the digest filed it. In a tool whose
subject is machine identity, "who did this" is the question the interface should
answer without being asked — which is also why the connections page shows which
Jira account a connection acts as, and the API keys page leads with when each
key was last used. A key never used, or unused for months, is a non-human
identity worth retiring, and the interface should make that obvious.

**The account is always on screen.** Tenancy is the central idea, and a person
should never be unsure which account they are acting in.

### Waiting for a durable workflow

Filing a ticket starts a Temporal workflow and waits up to eight seconds. Under
that, the response carries the issue key and the interface shows a link. Over
it, the API returns `202` and the interface says the ticket is still being
filed and will appear in the list. The workflow keeps retrying either way, so
the slow path is honest rather than a failure.

### What was deliberately not built

No design system, no state management library beyond the query cache, no form
library where two controlled inputs suffice, no toast system where an inline
message is clearer. Each would be defensible in a product with more surface;
here they would be weight without load.

## 9. Scope boundaries

**In scope**: password sign-in and server-side sign-out, signed access tokens,
Jira connection per tenant, project + issue-type discovery, ticket creation via UI
and API, recent-tickets view, API keys, audit log, blog digest.

**Explicitly out of scope**, with reasoning:

| Excluded | Why |
|---|---|
| Kubernetes / Helm | Compose satisfies "frictionless"; k8s adds setup friction for a reviewer |
| Message queue | No async workload justifies one; the digest is a scheduled binary |
| Inbound Jira webhooks | Would need a public callback URL; breaks local-first setup |
| Full RBAC | Two roles (member, admin) cover the flows; a policy engine is unjustified here |
| Multiple Jira sites per tenant | Schema supports N connections; UI assumes one active |
| A second connector | The seam is built and argued for in §3; building GitHub too would demonstrate nothing the seam does not |
| Brute-force lockout on sign-in | The free half is done — an unknown address costs the same as a wrong password, so timing cannot be used to enumerate accounts. The counting half needs a per-identity counter, a window, a threshold, a disable period and an unlock path: state, policy and a support flow, each a product decision this exercise does not ask for. In production the identity provider owns sign-in and ships this already |
| Refresh tokens and idle timeout | Renewing a credential is the provider's side of the exchange. One hour absolute is the bound |
| Binding a token to an IP or User-Agent | Rejected on the merits, not skipped — see §2a. Both cost real usability and buy little; the mechanisms that actually stop token theft are refresh-token rotation and sender-constrained tokens, and both belong to the provider |
| A JWKS-verifying resolver | The seam is `auth.TokenResolver` and the token shape is already a provider's, so the change is one implementation — but "one file" stays an argument rather than a demonstration until someone writes it |
| Request-body validation from the spec | The document validates *responses* in the test suite; requests are validated by hand in `validate.go`, which produces field-level errors in this API's envelope that the generic validator does not |

**Where this goes next.** The natural extension for an NHI platform is inverting the
connector: scanning Jira for *its own* non-human identities — app links, webhooks, bot
accounts, personal access tokens on service users — and filing findings about them.

That work needs no new seam. It is a second capability alongside
`capabilities/issuetracker` — say `capabilities/identityscanner`, another handful of
action names and shapes — implemented by the same `jira` connector, which already holds
the credential and the client. `connector` would not change, and a connector that can
scan but not file, or file but not scan, is expressible: the two capabilities are
checked independently. That is the payoff of keeping the port free of any particular
capability's vocabulary.
